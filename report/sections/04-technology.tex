\section{Technology Stack and Integration}
\label{sec:tech}

Every part of \proj{} runs on the client, inside the browser. The system is
assembled from a small set of web technologies, each chosen for one job, and the
engineering value is largely in how they are \emph{coordinated}. This section
catalogues the stack, explains how each piece is used, and then shows how they
fit together as a single pipeline.

\subsection{How Each Technology Is Used}
\begin{description}[leftmargin=1.4em, style=nextline]
  \item[Chrome Extension (Manifest V3).] The \code{manifest.json} declares the
        \code{storage} and \code{declarativeNetRequest} permissions, exposes the
        viewer and bundled libraries as \code{web\_accessible\_resources}, and
        sets a content security policy of \code{script-src 'self'
        'wasm-\allowbreak unsafe-\allowbreak eval'} --- the last clause is what
        permits Tesseract's WebAssembly core to execute inside the extension.
  \item[Service worker, \code{chrome.action} \& \code{chrome.commands}.] The
        service worker stays dormant until the user invokes the extension on a
        PDF---either by clicking the toolbar icon (\code{action.onClicked}) or by
        pressing the keyboard shortcut (\code{commands.onCommand}, default
        \code{Ctrl+Shift+F} / \code{Cmd+Shift+F}). Both
        run the same handler, which switches the active tab to
        \code{viewer.html?url=\dots}\ (or, if the tab is already the viewer,
        switches it back to Chrome's native viewer). Section~\ref{sec:design}
        explains why activation is on demand rather than automatic.
  \item[PDF.js.] \code{getDocument(\{url\})} loads the file; per page,
        \code{getViewport(\{scale\})} sizes it and \code{render()} draws it to a
        canvas. \code{getTextContent()}
        yields native text items, and \code{getOperatorList()} (checked against
        \code{pdfjsLib.OPS} image operators) reveals whether a page paints
        raster images. The \code{viewport.transform} matrix anchors the
        coordinate mapping of Section~\ref{sec:design}.
  \item[Canvas API.] Each page is rendered twice: an on-screen canvas whose
        backing store is scaled by the device pixel ratio for sharpness, and a
        separate offscreen canvas targeting $\sim$3000\,px wide for OCR. \code{getImageData}
        / \code{putImageData} give the preprocessing stage pixel-level access.
  \item[Tesseract.js.] Loaded as a UMD script that exposes \code{window.Tesseract}.
        A \code{createScheduler()} fronts a pool of \code{createWorker()} LSTM
        workers configured with \code{PSM.SPARSE\_TEXT}; an
        \code{addJob("recognize")} call (with \code{blocks:true}) returns the
        block\,$\to$\,word hierarchy with bounding boxes. The WASM cores and \code{eng}/\code{dan} language data
        are bundled locally, so OCR is fully offline. Three language modes are
        supported: English (\code{eng}), Danish (\code{dan}), and combined
        English+Danish (\code{eng+dan}).
  \item[Web Workers \& scheduler.] OCR is CPU-bound, so it never runs on the
        main thread. The scheduler distributes pages across
        $\min(4,\,\text{cores}{-}1)$ workers, keeping the UI responsive while
        several pages recognize in parallel.
  \item[IndexedDB.] \code{cache.js} stores each page's recognized words under a
        \code{\$\{docId\}::\$\{pageNum\}} key, with coordinates normalized to the
        unit square and a \code{FORMAT\_VER} stamp that invalidates results when
        the pipeline changes.
  \item[\code{localStorage} \& DOM APIs.] The OCR language is remembered in
        \code{localStorage}. The recovered text becomes invisible \code{<span>}s;
        \code{Range.getClientRects()} provides exact geometry for find
        highlights; \code{IntersectionObserver} triggers lazy rendering; and
        \code{requestIdleCallback} paces background indexing.
\end{description}

\subsection{Coordination Between Technologies}
\code{viewer.js} is the orchestrator: it owns the page lifecycle and brokers
every hand-off between the libraries. Figure~\ref{fig:integration} traces the
data that crosses each boundary. On the user's trigger the service worker opens
the PDF in the viewer;
PDF.js rasterizes pages to canvas and reports their text and image operators;
image pages are sent (as a high-resolution canvas) to the Tesseract worker pool,
which returns words and boxes; those words are normalized and persisted to
IndexedDB; and finally the orchestrator emits the invisible DOM text layer that
the find bar searches. Each technology only ever talks to \code{viewer.js},
which keeps the coupling between them loose and the data contracts explicit.
