\section{Results and Evaluation}
\label{sec:results}

The system is evaluated by an automated end-to-end test of the \emph{packaged}
extension in real Chrome, complemented by measurements of OCR accuracy, timing,
and visual fidelity on a small set of test documents. The corpus is small and
synthetic, so the accuracy figures characterize behaviour rather than serve as a
benchmark (Section~\ref{sec:limitations}).

\subsection{Method: End-to-End Testing in Chrome}
The test (\code{npm run test:e2e}) builds the release zip, unpacks it, and
launches Google Chrome with a throwaway profile, connected through the DevTools
protocol over a pipe~\cite{cdp}. It loads the extension with
\code{Extensions.loadUnpacked}, attaches to the extension's service worker,
and invokes the same handler the toolbar icon calls. A local HTTP server plays
the web: it serves image-only PDFs, a PDF at a URL without ``.pdf'', a PDF behind
a sign-in cookie, a URL whose file changes between requests, a non-PDF page, and
two encrypted PDFs. The fixtures are US Letter pages rendered at 300\,DPI and
saved as image-only PDFs, like a scanner's output: a dense page with a paragraph,
small print and a bordered table; a sparse receipt-like page; and a delivery note
with a table. Each check observes what Chrome actually did---the tab's URL and
title, the toolbar badge---and reads the copy back out of Cache Storage to
extract its text with an independent PDF.js instance.

The suite's most important result came before it passed. Its first run showed
that the shipped design never completed the tab switch---OCR finished and the
copy existed, but Chrome would not navigate the tab to a \code{blob:} URL. No
earlier test could have noticed, because none involved Chrome's own tab
navigation. The redesign of decision~\ref{dec:serve} followed directly.

\subsection{OCR Accuracy}
On the dense page, the copy's text layer contains all 74 words, including the
small print and every table cell; one character was misread (``ZX-4471'' as
``7X-4471''). The sparse page and the delivery note were recognized word for
word, including their tables. The gain cap of Eq.~\eqref{eq:stretch} was decisive
on sparse pages. On the first, oversized test pages, the uncapped stretch turned
one page into unrelated fragments and broke words in another's headline
(``Qu erly S ary'' for ``Quarterly Summary''); with the cap, both read correctly.

Two observations temper these numbers. The fixtures are clean renders, kinder
than real scans with skew, noise and uneven lighting. And the 3000\,px OCR
resolution is tuned for ordinary type sizes: on test pages with unusually large
text, Tesseract skipped bordered table cells that it read at half the
resolution.

\subsection{Speed and Size}
Measured by the test harness on the development Mac (at 0.5\,s polling
granularity), a one-page scan goes from the user's gesture to the searchable copy
on screen in about 2--2.5\,s, including starting the OCR workers. The same file
again---even from another URL---takes about 0.5\,s, as OCR is skipped, and a
new document after the workers have been released takes about 1\,s. Multi-page
documents scale with the page count divided by the number of workers.

The release package is 8.5\,MB. Shipping only the two Tesseract builds that can
actually load (of the six previously bundled, each in three file formats) cut it
from 22.5\,MB.

\subsection{Visual Fidelity}
Invisible text paints nothing, so the copy should look exactly like the
original. When the sandwich design was introduced, the original and the copy
were rendered and compared pixel by pixel: 0 of 2{,}298{,}825 pixels differed.
The end-to-end suite additionally checks that the page count and the tab title
are unchanged. Everything the user sees---toolbar, find bar, highlights,
context menu---is Chrome's own.

\subsection{Discussion}
The results support the project's central thesis in its strongest form: by
turning the document into real text, the system inherits not only the browser's
search but its entire PDF experience, and adds no interface of its own. The
engineering effort concentrated where the real difficulty lay---placing words
precisely in PDF space, keeping a CPU-heavy workload in the background, and
fitting into what the browser allows an extension to do. The last of these is
also the lesson of the evaluation: only testing the packaged extension in the
real browser revealed whether the product worked at all.
