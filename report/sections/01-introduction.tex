\section{Introduction}
\label{sec:intro}

\subsection{Motivation}
Documents on the web fall broadly into two categories. \emph{Text-based} PDFs
embed their characters as selectable, searchable glyphs and work seamlessly with
the browser's built-in find feature. \emph{Image-based} documents---scanned
pages, photographs of text, screenshots, and PDFs whose text has been flattened
into raster images---contain no machine-readable text at all. To the browser
they are pictures. Pressing $\mathrm{Ctrl}{+}\mathrm{F}$ on such a document finds
nothing, even though the text is plainly visible to a human reader.

This is a pervasive friction point. A student searching a scanned textbook, a
researcher scanning archival material, or anyone working with a faxed or
photographed form repeatedly hits the same wall: the content is \emph{there}, but
not \emph{findable}. The conventional remedy---uploading the file to a
server-side OCR service to produce a new, searchable PDF---is slow, raises
privacy concerns, and breaks the natural in-browser reading flow.

\subsection{Key Idea}
\proj{} does not build a search engine. Instead, it \emph{makes the document
itself searchable} and leaves searching to the browser. It recovers the text
baked into images with on-device OCR and writes that text back \emph{into the
PDF} as an invisible layer, the same ``searchable scan'' technique that document
scanners use. Chrome's own viewer then opens the result. From the browser's
perspective the document now \emph{contains} text, so Chrome's mature find,
highlighting, selection, and copy machinery applies unchanged.

Two convictions shaped the project. The first is that \emph{the cheapest way to
make something searchable is to make it real text}, rather than intercepting and
re-implementing search. The second came from the user later in the project: the
extension must not present a different view at all. Chrome's own viewer, toolbar
and find bar must be the only interface, and the PDF must look exactly as it
did. The final architecture satisfies both by changing \emph{what} Chrome
displays (a searchable copy) rather than \emph{how} it displays it.

\subsection{Contributions}
This report documents the design and implementation of \proj{}. Its principal
contributions are:

\begin{itemize}
  \item A fully \textbf{client-side, offline} pipeline that turns a scanned PDF
        into a searchable one inside the browser, with no server round-trip and
        no data leaving the user's machine.
  \item A \textbf{native-viewer-only delivery model}: OCR runs in an offscreen
        document, and the searchable copy is served from the extension's own
        origin by its service worker, so Chrome's built-in viewer displays it
        with the original's tab title (Section~\ref{sec:design}).
  \item A \textbf{coordinate mapping} from OCR pixel boxes into PDF user space,
        including rotated pages. Each invisible word is sized and horizontally
        squeezed so that Chrome's native find highlight covers the visible word
        (Section~\ref{sec:design}).
  \item An \textbf{OCR accuracy layer}: high-resolution rendering, gain-capped
        contrast stretching, sharpening, and post-processing that corrects
        likely digit/letter confusions (Section~\ref{sec:impl}).
  \item \textbf{Content-addressed caching and bounded resources}: OCR results
        keyed by a SHA-256 hash of the file, least-recently-used pruning, and
        automatic release of OCR workers and searchable copies.
  \item An \textbf{end-to-end test suite} that loads the packaged extension into
        real Chrome and verifies the whole user journey
        (Section~\ref{sec:results}).
\end{itemize}
